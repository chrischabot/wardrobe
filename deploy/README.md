# Development deployment on Cloudflare

This directory deploys the fresh Garderobe build to **development** resources on Cloudflare, verifies it there over HTTPS, and removes it again. It contains no product logic: the Workers it uploads are `apps/worker` unchanged, plus one operations Worker (`deploy/ops`) that seeds and probes.

**State on 2026-10-03: nothing is deployed.** The tooling is complete and has been run end to end against local simulators, but the management token it needs (`CLOUDFLARE_API_TOKEN`) is set as a project secret and is not delivered to the build sandbox, so no resource could be created. See `evidence/README.md` for what was and was not run.

## Commands

Run from the repository root after `npm ci`.

| Command | What it does |
| --- | --- |
| `node deploy/probe-access.mjs` | Read-only: which required variables are present (names only) and which services the credentials reach. Exit 0 means the deploy command can run. |
| `node deploy/deploy.mjs --commit <sha>` | The one command: provisions what is missing, applies every migration, uploads the three Workers with their application secrets, seeds through the real importer, compares the result with the local import, writes `evidence/deploy.json`. Safe to run again. |
| `node deploy/deploy.mjs --dry-run` | Reads the account, lists what would be created, builds the Workers without uploading. Writes nothing remote. |
| `node deploy/verify.mjs [--restart]` | Verification over HTTPS against the deployment; writes `evidence/verify-dev.json`. `--restart` redeploys the product Worker between two reads of a conversation. |
| `node deploy/teardown.mjs` | Dry run (the default): lists exactly what would be removed. `--confirm garderobe-rebuild-dev` removes it. |
| `node deploy/rehearse.mjs` | Local rehearsal on Miniflare: migrations, seed, reconciliation, the verification checks that have a local simulator, and a build of the three deployment configurations. Not a deployment. |
| `node --test deploy/test/guard.test.mjs` | The guard's tests (no network, no credentials). |

Environment: `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` (project secrets). Optional `GARDEROBE_OWNER_EMAIL`: the one identity the Access application admits at the person's door; without it that door admits nobody.

## What is created

Every name starts with `garderobe-rebuild-dev`. The guard in `lib/config.mjs` refuses any other name, any hostname outside `garderobe-rebuild-dev*.chabot.dev`, and any `--env` other than `dev`; a management write cannot be made without passing it (`lib/cf.mjs`).

| Kind | Name |
| --- | --- |
| Workers | `garderobe-rebuild-dev` (product: API, MCP, conversation Durable Object, queue consumer, five-minute cron), `garderobe-rebuild-dev-auto` (the same product entry on the automation hostnames), `garderobe-rebuild-dev-ops` (seed, probes, one probe Workflow) |
| Hostnames | `garderobe-rebuild-dev.chabot.dev` (app, behind Access), `garderobe-rebuild-dev-mcp.chabot.dev` (MCP), `-auto` and `-auto-mcp` (automation door), `-ops` |
| D1 | `garderobe-rebuild-dev`, all files in `migrations/` |
| KV | `garderobe-rebuild-dev-oauth` (MCP OAuth provider) |
| R2 | `garderobe-rebuild-dev-media`, `garderobe-rebuild-dev-exports`; the public `r2.dev` address is switched off and no custom domain is attached |
| Queues | `garderobe-rebuild-dev-media` with consumer (batch 5, 3 retries) and dead-letter queue `garderobe-rebuild-dev-media-dlq` |
| AI Search | namespace `garderobe-rebuild-dev`; the application creates one private instance per internal user |
| Access | one application on the app hostname, and a bypass for `/connections/callback` and `/v1/media/signed/*`, which authenticate themselves |
| Bindings without a resource of their own | `AI` (through the gateway below), `IMAGES`, `BROWSER` |

Declared and never created or changed: the owner's AI Gateway `garderobe-dev` (specification section 19). Everything else on the account, including the earlier application's `garderobe-dev-media`, `garderobe-images` and `garderobe-dev-recall`, is listed in the evidence as found and is left alone.

## Sign-in, and what the automation door is

The product Worker verifies a Cloudflare Access assertion against the public keys at `ACCESS_TEAM_DOMAIN/cdn-cgi/access/certs`, and MCP access is a grant from the Worker's own OAuth server. Neither is a Cloudflare management credential, and none is bound to any Worker (`deployWorkers` in `lib/management.mjs` refuses to; the guard test checks the generated configurations).

A person signs in at the app hostname through Access with Google. A script cannot do that, so verification uses a second deployment of the same product code, the automation door, whose issuer is a key generated by this tooling and whose public half the operations Worker serves at the same certificate path. It is the application's ordinary assertion check with a different issuer; nothing in the product is changed or relaxed. Three labelled test identities use it: the owner (linked to the imported account by a real invitation and claim), a synthetic second owner, and a stranger linked to nothing. The automation door exists only in development and teardown removes it. Consequence to keep in mind: whoever holds the local state file can sign in to the development copy of the owner's data through that door.

Local state is `deploy/.wrangler/state/dev.json` (git-ignored, mode 0600): generated application secrets, the automation key, the operations token, one-time invitation codes. Keep it between runs; without it a redeploy generates new application secrets.

## Seeding

The operations Worker imports `requirements/chris-wardrobe-profile.md` and `requirements/wardrobe_inventory_clean.csv` (bundled byte for byte; the importer checks the profile hash) through `importOwnerData` and the ordinary command service, then creates a labelled synthetic second owner with three synthetic garments. The seed is idempotent and resumable: a call that runs out of its per-invocation database budget is repeated and continues. The deploy command then compares garments, units, an inventory digest, the profile hash, rules, measurements, restrictions and command count with `evidence/reference-import.json`, the same import into a fresh local database, and fails if anything differs.

```js
import { clientFor, targetFor, callTool } from "<repo>/deploy/lib/http.mjs";
import { readState } from "<repo>/deploy/lib/state.mjs";
const c = clientFor(targetFor("deployed"), readState());     // or targetFor("rehearsal") with `node deploy/rehearse.mjs --keep`
const me = await c.api("GET", "/v1/me", undefined, { as: "synthetic" });
const mcp = await c.connectMcp({ write: true, as: "synthetic", clientName: "Journeys" });
const today = await callTool(mcp.client, "garderobe_today", {});
```

Write to the synthetic owner or to labelled synthetic garments only; never record wear on the owner's real stock.

## What only the owner can supply

- **Management token in the sandbox.** `CLOUDFLARE_API_TOKEN` must reach the environment the deploy command runs in.
- **Cloudflare Access.** A Zero Trust organization with Google as identity provider, and `GARDEROBE_OWNER_EMAIL` so the Access application admits the owner. The owner then opens the app hostname, signs in and claims the account with the invitation code stored in the local state.
- **Google Calendar.** An OAuth client in the dedicated Google Cloud project (`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` as Worker secrets, redirect `https://garderobe-rebuild-dev.chabot.dev/connections/callback`), the owner's own Google sign-in in the app, and the choice of the outfit calendar.
- **Apple WeatherKit.** An Apple Developer team with a WeatherKit key and service ID. Until then the forecast source is Open-Meteo.
- **Tavily.** The key is on the owner's own machine (specification section 19); it is added as a connection in the app.
- **Push notifications.** An APNs key (`APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY`, `APNS_TOPIC`).

## Known limits of this tooling

- Application secrets are uploaded as Worker secrets with `wrangler deploy --secrets-file`; Secrets Store (specification section 14) is not used.
- The product Worker exports no Workflow class, so the only Workflow on the deployment is the operations Worker's probe.
- Model probes are recorded with `inference.record_probe` only on positive evidence of Unified Billing (the response's key source, or the Gateway's own log entry for that call). When neither shows it, nothing is recorded and the profile stays unselectable.
- The request shapes for Access applications, the Queues pull API and AI Search were taken from the published API schema and have not been exercised against the account.
