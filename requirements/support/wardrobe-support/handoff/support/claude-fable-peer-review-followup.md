**Verdict up front:** Revision 3 is implementable with targeted fixes. No finding below reverses an architectural decision. Two are design contradictions (weather rule, compaction budgeting); the rest are implementation probes that Phase 1/2 exit criteria should name explicitly. I cannot independently verify platform claims dated after mid-2026 (MCP 2026-07-28, Think APIs, Browser Run, Access Managed OAuth); I treat them as the document's own probes.

## Findings

**1. The 14–16 °C layering rule has no temperature basis and inconsistent strength. Design issue.**
The design's own weather principle is two-basis: base layers follow daytime peak, outerwear follows departure conditions (sections 6 and 7). The 14–16 °C rule couples a base layer (light oxford) to an outer layer (jacket) and never states which reading the interval applies to. Its strength also drifts: section 6 lists hard rules as availability, socks and footwear only; the section 7 rule table says "evaluate the combined layers and walking context" (soft); the section 7 weather paragraph calls it "the explicit light-oxford-only rule" that rain cannot override (hard). A day at 12 °C departure and 17 °C peak cannot be validated deterministically as written. Section 9 separately promises a "weather observation within an hour" while section 7 defines the target as fetch time, not issue time. Fix: assign the interval to one basis per garment role, place the rule on the hard/soft list once, and define the reference window for outfits composed after the peak (dinner outfit, evening return), which section 7 lists as a distinguished window but never gives a rule.

**2. Deletion depends on Think Session capabilities the design has not established. Design issue plus probe.**
Section 6 requires deleting source messages, invalidating summaries that carry personal facts, and regenerating them. The only Think API behavior asserted is that `getHistory()` applies compaction overlays and that compaction is driven by `onCompaction`. Nothing asserts per-message deletion or overlay regeneration over a modified history. Section 20 says the raw-history spike covers delete, but the Phase 1 exit criterion lists only export and restore. If Session cannot delete, the fallback must be specified now: read-time redaction tombstones in the transcript adapter plus forced re-compaction of affected ranges. Two stores also sit outside the deletion list: Browser Run session recordings (adopted in the section 14 table) and Workflow step results, which retain page content and evidence envelopes. Add both to the deletion and retention scope.

**3. Native login trust boundary: a public client with "client credentials in Keychain". Probe.**
Section 15 says Managed OAuth client credentials are stored only in Keychain. A native app is a public client; any embedded secret is extractable, so the design should not rely on it for anything. The probe must confirm Managed OAuth supports a secretless PKCE public client with the resource indicator; if a secret is mandatory, treat it as non-secret and rely on PKCE plus redirect-URI binding, and say so. Related path carving is unstated: the same hostname must exclude from Access the MCP resource endpoint, the OAuth token and revocation endpoints, `/.well-known/*`, the SSE run stream, and the Google Workspace OAuth callback, which arrives from the system browser without an Access session and is authenticated only by bound state. Section 15 gestures at this ("not a second Access OAuth challenge") but Phase 1 should list the exempt routes and test that each rejects forged identity headers.

**4. Automatic compaction and overflow recovery bypass the spend reservation gate. Design issue.**
Section 12 requires reserving spend in the D1 ledger before every dispatch. Section 6 lets Think trigger compaction via `compactAfter` and mid-turn overflow recovery, with the compaction model routed through Gateway. Routing is satisfied; reservation is not, because the harness decides when to infer. Either `onCompaction` must call the application model service and reserve first (and fail closed with a resumable turn when the budget is exhausted), or the design must state that compaction settles post hoc within a fixed daily ceiling. The same applies to AI Search query rewriting and reranking if enabled. State which.

**5. Per-user AI Search instances need an account-level management credential the design otherwise avoids. Probe.**
Section 6 provisions one instance per internal user ID; section 19 records that management endpoints rejected the available Wrangler OAuth token. Runtime instance creation requires a scoped API token in Secrets Store, plus item upload, delete and status calls through the Workers binding. For a single owner, pre-provisioning the two instances (dev, prod) by hand removes the runtime credential entirely; the design should pick one path. Also confirm before indexing: the five-field metadata limit, string-index limits, and whether the per-tenant guidance actually recommends instance-per-tenant or filter-per-tenant, since the isolation argument rests on it.

**6. One inference accounting path is asserted, but two settlement ledgers are likely. Probe.**
Section 12 uses Unified Billing prepaid credits as the accounting boundary; section 19 selected "Workers AI Unified Billing" on the gateway; section 14 says AI Search model usage is "separately chargeable". If Workers AI consumed by AI Search or Agent Memory settles as account usage rather than credits, monthly spend reconciliation must read two sources, and the section 14 "free operation" gate must include Workers AI neurons. Also unverified: the "beta spend limit controls" referenced in section 19 step 1, and the current auto-refill state (section 12 says it "starts disabled"; section 19 says no change was made, which does not establish it is off). Confirm both before automated traffic.

**7. Browser Run's 10 daily free minutes are claimed by four consumers. Budget probe.**
Image backfill (section 11), interactive variant checks and structured extraction (section 10), Playwright MCP sessions, and AI Search website crawling all draw on Browser Run. Section 14 asserts crawling sits inside AI Search's open-beta allowance rather than the daily minutes; that is unverified and, if wrong, the 60–120 day backfill estimate and the 5-minute interactive reserve both collapse. Live View and human handoff may also be paid-plan features. The section 17 free-plan viability test should meter browser minutes by consumer and confirm which count against the daily limit.

## Verdict

Proceed to Phase 1 after amending the weather rule (finding 1) and the compaction budgeting rule (finding 4), which are contradictions within the text. Add findings 2, 3, 5, 6 and 7 as named exit criteria for the existing Phase 1 and 2 spikes rather than new work. Nothing here requires revisiting Cloudflare platform adoption, developer previews, managed AI Search, Google-backed login with internal IDs, Tavily plus Browser Run, or the preloaded weather skill.
